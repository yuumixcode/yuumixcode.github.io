### ADR 是什么

任何「做了就不好改」的决定，都写一篇 ADR，放在 `10-design/adr/`，文件名 `NNNN-短标题.md`（如 `0003-用-scriptableobject-存配置.md`）。模板只要四段：

```markdown
# 0003 用 ScriptableObject 存配置

- 日期：2026-01-01
- 状态：已采纳 / 已废弃（被 0007 取代）

## 背景
（当时面对什么问题、有什么约束）

## 选项
（考虑过哪几条路，各自的代价）

## 决定
（选了哪个，为什么）

## 后果
（要接受什么代价、以后什么条件下应该推翻它）
```

**为什么值得写**：三个月后没人记得为什么这么做，重做一遍的成本远高于写这四段。

## 3. 写文档的三条铁律

1. **新增文档必须在本文 §2 加一行，否则视为不存在。**
   没人知道存在的文档 = 没有文档。索引是唯一入口。

2. **一篇文档只回答一个问题。**
   不要写「大而全的设计圣经」。写长了就拆，拆完在索引里各占一行。

3. **过时的文档要么改、要么删，不留「半对」的内容。**
   半对的文档比没有文档更危险——它会让人做出错误决定。

---

## 4. 找不到 / 文档过期了怎么办

- **找不到**：先搜仓库（网页端搜索框搜关键词），还没有 → 问 §2 里该目录的维护人 → 得到答案后**由提问的人**写成文档并加索引（谁问谁写，避免同一问题被问三次）
- **发现过期**：直接在文档顶部标 `> ⚠️ 已过期，见 [新文档](路径)`，然后提一个 issue；不要默默绕过
- **有争议**：不要改文档，先开 issue 讨论，结论落地成 ADR

---

## 5. 提交约定

- 改文档和改代码走同一个 PR，**不要单独攒一批文档提交**
- 提交信息带 issue 号：`docs: 补充数值表说明 (#123)`
- 文档里的链接一律用相对 `.md` 路径（`../20-tech/coding-standard.md`），不要用绝对 URL —— 这样在代码托管平台的网页端也能直接点开
