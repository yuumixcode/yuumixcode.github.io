不用慌。

这不是又一篇命令清单。我们把 commit、push、pull、fetch、rebase 拆成看得见的动画，再让两个开发者 A 和 B 面对面地演示一遍：从"我该先提交还是先拉取"，到"这行代码到底该听谁的"。 全程你只需要点按钮。

01

先记住四个区，Git 就不神秘了

Git 的一切操作，本质上只是在这四个"容器"之间搬运文件。搞懂搬运路径，所有命令都能自己推出来。

工作区
Working Directory
你正在编辑的文件夹。你在 IDE 里看到的代码就在这里，它还没有被 Git 记住。
git add
暂存区
Staging Area
你的"待提交清单"。这一步最容易被忽略，但它是 只提交一部分改动 的唯一办法。
git commit
本地仓库
Local Repository
你电脑上的 .git 目录。这里已经有完整历史，但只有你自己看得到。
git pull git push
远端仓库
Remote / origin
GitHub / Gitee 上的那份。它是团队的唯一真相——只有推上去，别人才拿得到。
💡
一句话刻在脑子里：commit 是"存草稿到自己的 U 盘"，push 是"把 U 盘内容上传到团队网盘"。 没 push 之前，你的工作在别人眼里等于不存在。
⚠️
新手第一大坑：以为 commit 了就等于"保存到项目"了。 你 git add 一堆、切个分支、git checkout 一下，代码可能就没了——因为它只在工作区，Git 根本不认识。 改完代码先 commit，这是最便宜的安全带。
02

五个命令，各自到底做了什么

把网上那些互相抄的定义全扔掉。用"货物运输"来理解，五分钟就够。

git add . 本地

📦 打包：把工作区里选中的文件放进待提交箱子。

  • 不执行 add，commit 会报 nothing to commit（新文件）或只提交已 add 的部分
  • 新手最常用 git add .，更精准的是 git add 路径/文件.cs
  • 大型项目（Unity 的 Library/、Temp/）务必先进 .gitignore
git commit -m "..." 本地

📸 拍照存档：给当前这一刻的项目拍一张不可篡改的快照。

  • 每个 commit 有一个唯一哈希（如 a3f9c21），这是你未来的"撤销键"
  • 一次 commit 应该只干一件事，别把修 bug 和改文案揉一起
  • 提交信息写"为什么"而不是"改了什么"——后者 Git 自己会 diff 出来
git push 网络

📤 上传：把本地仓库里的提交同步到远端。

  • 注意是"上传本地已有的"，不会凭空下载别人的东西
  • 远端有你没见过的新提交时，push 会被拒绝（non-fast-forward）
  • 被拒绝是 Git 在保护你，不是报错，先去 pull 就行
git fetch 网络

👀 只看不碰：下载远端最新情况，但绝不改你的代码。

  • 下载后你本地多出一个 origin/main，它只是远端的快照
  • 你的工作区、暂存区、本地分支，一个字节都没变
  • 这是"我先看看别人干了啥"的零风险动作，强烈建议形成习惯
git pull 网络

📥 下载并合并：fetch 完顺手把别人的改动并进你的分支。

  • 技术等价于 git fetch + git merge，只是省了一步
  • 会改你的代码，所以之前必须先 commit 保护现场
  • 可能撞出冲突，冲突怎么办 → 往下看

最值得记住的对比：fetch 和 pull 差在哪？

它们开头做的事完全一样，区别只在最后一步——要不要动我的代码。

git fetch origin
你的本地
代码不动
$ git fetch
远端
下载快照
✅ 新增 origin/main 引用
✅ 你的文件一个都没变
➖ 想合并？自己再敲 git merge
git pull origin main
你的本地
待命
$ git pull
远端
下载快照
⚠️ fetch（下载）
⚠️ merge（动你的文件）
➖ 前提：本地改动必须先 commit
🎯
实用习惯：开工前先 git fetch 摸清情况，想清楚了再决定用 merge 还是 rebase 来整合。 对初学者来说，"先 fetch 看看" 能避免掉进绝大多数"我是不是把别人代码覆盖了"的恐慌里。
03

分支：本地分支和"远程分支"其实是两个东西

很多人第一次看 git branch -a 输出就懵了：为什么 main 和 origin/main 是两个分支？ 因为它们真的就是两份独立的数据。

点一下，看看两个仓库各自的样子

远端 origin GitHub 上的那份
main 真实分支
A 的电脑 本地仓库
main 真实分支
origin/main 远端跟踪
B 的电脑 本地仓库
main 真实分支
origin/main 远端跟踪
💡
origin/main 不是"远程的 main"，它是"我上次 fetch 时看到的远程 main 照片"。 远端后来又变了，origin/main 不会自动更新——必须再 git fetch。 所以 origin/ 开头的东西只作参考，永远不要直接在上面改代码。
分支是干什么用的
  • 隔离改动：你在 feature/login 上写一半能跑的东西，main 依然干净可交付
  • 并行开发：A 在 feature/audio，B 在 feature/ui，互不干扰
  • 救火专用：线上出 bug 从 main 拉 hotfix/xxx，修完直接合回去
分支的三个日常命令
  • git switch -c feature/login新建并切过去
  • git switch main切回主干
  • git switch -立刻跳回上一个分支（超常用）
提交前看一眼自己在哪

命令栏里 git status 第一行永远会告诉你当前分支：

On branch feature/login
Your branch is up to date with 'origin/feature/login'.

如果显示 detached HEAD，说明你不在任何分支上（常见于直接 checkout 了 commit id）。 别慌，代码没丢，敲 git switch - 回分支即可。

05

文件被覆盖时，到底发生了什么

"两个人改了同一个文件的同一行"——这是新手最怕的场景。下面把它拆开：冲突是怎么产生的、那些尖括号是什么意思、该怎么判。

1

你和同事从同一个点出发

你们的分支都从 commit c1 分叉出去。Git 知道大家起点一致，这是安全的。

2

你们分别提交了

A 产出 a1，B 产出 b1。两份历史现在分叉了，谁也不包含谁。

3

合并时撞在同一行

Git 发现两边都改了 maxHealth 这一行。它没有权力替你决定谁对，于是停下来问你。

PlayerHealth.cs
合并冲突后的文件长这样

      

        

          
          
<<<<<<< HEAD你的这一侧（你当前所在的分支）

        

        

          
          
|||||||共同祖先（你俩分叉前的版本，只作参考）

        

        

          
          
>>>>>>> origin/main对方这一侧（被合并进来的远端）

        

      

    


    

      
正确的解决顺序（别跳步）

      

        

          
1

          

            
先 git status 看清全局

            
Git 会列出所有冲突文件，标记在 Unmerged paths 下。心里有个数：这次要处理几个文件。

          

        

        

          
2

          

            
读懂两边各自想干什么

            
这一步是分水岭。带着问题看代码：同事把 100 改成 80，是策划要求降血量还是手滑？
            不知道对方意图就动手合并，是把 bug 送进主干的最佳方式。

          

        

        

          
3

          

            
写下最终代码，删掉所有标记行

            
三个尖括号、三个等号、三个大于号，一个都不能留。最终结果可能是合并两份（比如两份 import 都要保留），不一定是二选一。

          

        

        

          
4

          

            
编译 / 跑一遍，确认能跑

            
别急着提交。Unity 项目至少让 Console 干净；再 git diff --check 扫一遍有没有漏网的标记。

          

        

        

          
5

          

            
git add 该文件 → git commit

            
解决一个就 add 一个，别攒到最后。Git 在你没 add 之前禁止提交，这是保护你。

          

        

      

    


    

      
核心原则

      
冲突时默认"以远端为主"，但不是无脑覆盖

      

        

          
✅ 应该保留对方

          
对方的改动有明确意图：他可能接了策划案、修了线上 bug、加了新的调用方。
          无脑覆盖 = 让团队重复劳动，Git 也会留下一个"你删了他代码"的提交记录。

        

        

          
🔧 然后接上自己的

          
把对方的结果当新基线，把你的改动在这条新基线上重新做一遍。
          冲突解决完的代码，往往既不是纯 A 也不是纯 B，而是第三种更完整的东西。

        

        

          
❓ 拿不准就问

          
不确定对方意图时，直接问人，一句"这行你是不是特意改的？"
          五秒钟解决，比猜错方向返工一小时划算得多。

        

      

    


    

      
🚨

      

        merge 和 rebase 的"流动方向"是反的，看一眼尖括号旁边就能分清。

        
第一层 · 直觉版（先记住这个）：

        
    
          
  • Merge —— 把对方收进来。你在 main 上把 feature/x 合并进来，你是接收方。
    • 
          
  • Rebase —— 把自己贴过去。你在 feature/x 上把自己的提交变基到 main 上面，你是发送方。
    • 
        

        
流向是反的，所以下面 --ours / --theirs 的指代才会反。


        
第二层 · 精确版（用到 --ours 之前再看一眼）：

        
    
          
  • 在 main 上 git merge feature/x：HEAD 是 main → --ours = main（你自己），--theirs = feature/x（对方）。
    • 
          
  • 在 feature/x 上 git rebase main：HEAD 物理上还是 feature/x，但 Git 内部是把 main 的最新提交当底座、重放你的提交——所以 --ours = main（这次合并的接收方），--theirs = feature/x 自己的提交。
    • 
          
  • 一眼分辨当前是 merge 还是 rebase：看冲突文件右侧尖括号旁边的字符串——
    
             · merge 写的是 >>>>>>> feature/x（分支名）
    
             · rebase 写的是 >>>>>>> 1c9a4e2（commit hash）
    
          看到 commit hash，就是 rebase——这时候的 --ours 指的是 main。
    • 
        


        
记忆窍门：--ours 不永远等于"我所在的分支"，而是"这次合并操作的接收方"。merge 和 rebase 的接收方不一样，标识符自然就反。

        所以用 --ours / --theirs 之前，先 git status 看清当前在哪个分支，再看一眼冲突标记旁边写的是分支名还是 commit hash。
      

    

  







  

    

      06
      
多人协作的七条铁律

      
下面每一条都对应一类真实事故。背下来，你就能少加班。

    


    

      

        
1

        

          
先 commit，再 pull

          
这是本课最重要的一条。pull 会改你的工作区，如果你有没提交的改动，Git 可能直接拒绝你，或者更糟——合并结果把那些改动搅乱。

          
✅ git status 确认干净 → git add . → git commit → git pull → 干活

          
为什么：commit 是快照，pull 只会在"两个版本"之间合并。工作区里的裸改动是"没有版本的文件"，它无处可去。

        

      


      

        
2

        

          
不要直接往 main 推代码

          
共享主干应该通过 Pull Request 合并，这样有人能看一眼、能跑测试、能留下讨论记录。

          
✅ git switch -c feature/xxx → 干活 → git push -u origin feature/xxx → 开 PR → 评审 → 合并

          
为什么：没有 PR 的推送意味着你既是作者又是裁判。团队规模一大，main 会变成谁都能改的公共黑板。

        

      


      

        
3

        

          
共享分支上永远不要 push --force

          
强推会直接抹掉远端历史——包括同事刚推上去、你本地还没拉到的提交。

          
✅ 被拒了就 git fetch → git pull --rebase → git push

          
为什么：Git 拒绝 non-fast-forward 推送，是它在替你踩刹车。真要强推，只用 --force-with-lease，且只对自己的私有分支用。

        

      


      

        
4

        

          
一次 commit 只做一件事

          
不要把「重构 + 修 bug + 改配置」打包成一个提交。

          
✅ 拆成三个 commit：refactor: 抽出工具类 / fix: 空引用 / chore: 调整配置

          
为什么：出问题时 git revert 只能整条撤销。混在一起的提交会连带撤掉别人的需求。

        

      


      

        
5

        

          
别在 .gitignore 上偷懒，Unity 项目尤其注意

          
Unity 的 Library/、Temp/、Logs/、obj/ 是自动生成的，几 GB 很正常，而且每次内容都不同。

          
✅ 忽略它们，只提交 Assets/、ProjectSettings/、Packages/

          
为什么：不忽略的话，clone 要下载几个 G，而且每次 pull 都会因为这些文件变化而产生假冲突——特别容易误导初学者以为自己改错了什么。

        

      


      

        
6

        

          
分支别养太久，冲突是攒出来的

          
一个分支开三周不合并，等你回来时它和主干的差距会制造大量本可避免的冲突。

          
✅ 勤 git fetch，分支存活控制在几天内；实在要拖就先 git rebase origin/main 同步一下

          
为什么：分叉越深，Git 能自动合并的部分越少，冲突概率呈指数上升。

        

      


      

        
7

        

          
三个救命命令，先背下来

          
遇到任何"我好像搞砸了"的时刻，先试这三个——它们几乎都能全身而退。

          

            git status 看现状 ·
            git log --oneline -10 看历史 ·
            git reflog 看被丢弃的提交还在不在
          

          
为什么：绝大多数"代码丢了"的事件其实只是"提交被改写了"。reflog 记录了 HEAD 的移动轨迹，包括那些看起来消失了的哈希——它几乎能从任何误操作里救回你的代码。

        

      

    

  







  

    

      07
      
团队通常怎么约定流程

      

        Git 本身对"团队怎么协作"没有意见，流程是团队自己定的。市面上主流的是下面这三种，选一种比什么都重要，选错的代价比不会大。
      

    


    

      

        
最常见 · 推荐初学者从这里开始

        
Feature Branch（GitHub Flow）

        
只有一条长期分支 main，任何改动都开一个短命分支，评审完就合掉删掉。

        
main      ●───●───●───●──●──●──▶
                \         /
feature/x     ●───●───▶

        
    
          
  • 适合：几乎所有小团队、SaaS、每天都在发版的项目
    • 
          
  • 优点：规则少到一句话说完，新人当天就能上手
    • 
          
  • 缺点：需要同时维护多个线上版本时不适用
    • 
        

      


      

        
最激进

        
Trunk-Based Development

        
几乎所有人都直接往 main 提交，分支只活几个小时，用特性开关（feature flag）藏住未完成的功能。

        
main   ●─●─●─●─●─●─●─●─▶
              ↑
       (未完成功能靠 flag 关闭)

        
    
          
  • 适合：CI 强、测试覆盖高、团队互信度高的团队
    • 
          
  • 优点：冲突最少，交付速度最快
    • 
          
  • 缺点：没有强 CI 和 flag 机制的话，main 天天崩，别学这个
    • 
        

      


      

        
经典但偏重

        
Gitflow

        
两条长期分支（main 存生产、develop 存开发中），外加 feature / release / hotfix 三类临时分支。

        
main      ●────────●────────▶ (tag v1.0)
              \      /
develop    ●──●─●─●─●─●─●─▶
             \        /
feature/x     ●───●─▶

        
    
          
  • 适合：Unity 插件、SDK 这类有明确版本号、要同时维护多个版本的软件
    • 
          
  • 优点：版本管理极其清晰，每个发版可追溯
    • 
          
  • 缺点：仪式感很重，个人项目和小型插件项目往往用不上，别硬套
    • 
        

      

    


    

      
🧭

      
给你（做 Unity 插件）的实际建议：
      先用最简单的 Feature Branch 跑起来——main 保持可发布，每个插件版本或每个功能开一个 feature/v1-2-aesir-inspector 这样的分支，合并时打 tag。
      什么时候需要 develop 分支？当你发现「main 上有些还没准备发布的东西」开始碍事的时候——到那时再引入不迟。
      

    

  







  

    

      08
      
进阶一点：rebase（变基）到底是什么

      

        rebase 常被说成"高级操作"，其实一句话就能说清：把你的提交拔下来，插到别的地方，然后重新拍一遍照。
        难的不是概念，是知道什么时候该用、什么时候绝对不能。
      

    


    

      

        
merge：加一条线，历史分叉后再汇合

        
        ●───●───M───▶  (main)
       /         /
      ●───●───●

多出一个 M 提交（"把 B 合并进来"这件事本身也成了一个提交）

      

      

        
rebase：把线拉直，历史是一条直线

        
                ●───▶  (main)
              /
        ●───●───●───●

你的两个提交被"重放"到了最新 main 后面，没有额外节点

      

    


    

      

        
✅

        

          
适合用 rebase 的情况

          
    
            
  • 整理自己还没推送的分支历史，让 log 好看、便于 review
    • 
            
  • 长分支开工前先同步主干：git fetch → git rebase origin/main，冲突会在你自己的分支上暴露，而不是等到 PR 时
    • 
            
  • 想让提交历史呈现为一条直线（很多团队最终合并时就 rebase + squash）
    • 
          

        

      

      

        
❌

        

          
绝对不要 rebase 的情况

          
    
            
  • 已经推送给别人的提交——rebase 会改写它们的哈希，导致所有人下一次的 push/pull 全乱套
    • 
            
  • main / develop 这类共享分支
    • 
            
  • 你"说不清刚才那个提交干了啥"的时候——rebase 出问题很难排查，先搞清楚再说
    • 
          

          
黄金法则：rebase 只在「这条线只有你一个人推过」的时候做。

        

      

    


    

      

        
rebase 中途冲突了怎么办

        每个提交都会停下来问你一次
      

      

        
git status看现在卡在哪个提交上

        
# 手动改文件解决冲突和普通冲突一样处理

        
git add 文件标记这个文件搞定了

        
git rebase --continue继续重放下一个提交

        
git rebase --abort想放弃？一键回到 rebase 之前

      

      
最后那条 --abort 请务必记住。rebase 会重写历史，中途觉得不对劲时，放弃重来永远比硬着头皮走下去安全——反正 rebase 前你一定是干净的。

    


    

      
🧭

      
对初学者的实用结论：merge 和 rebase 结果几乎一样（都是把两边的改动合到一起），区别只在历史长什么样。
      日常用 merge 完全没问题；等你开始嫌 git log 太乱、想让 PR 更好读时，再学 rebase 也不迟。
      先掌握 merge，别为了"显得专业"而上 rebase。

🔁 日常循环（90% 的时间都在做这些）

        

          
git status我在哪个分支？哪些文件改了？

          
git add .把改动放进待提交清单

          
git commit -m "..."存档一个快照

          
git push上传到远端

          
git pull下载并合并别人的改动

          
git log --oneline -10最近十个提交，一行一个

        

      


      

        
🌿 分支操作

        

          
git switch -c feature/x新建并切到 feature/x

          
git switch main切回主干

          
git switch -跳回上一个分支

          
git branch列出本地分支

          
git branch -a本地 + 远端跟踪分支

          
git push -u origin x首次推送新分支并建立关联

        

      


      

        
🆘 出问题了

        

          
git status冲突了？这里能看到全部冲突文件

          
git diff看具体哪里冲突了

          
git merge --abort放弃这次合并，回到之前

          
git rebase --abort放弃这次变基，回到之前

          
git restore 文件丢弃某个文件的本地改动

          
git reflog找回"消失"的提交

        

      


      

        
⚔️ 同步与冲突

        

          
git fetch origin只下载，不动我的代码

          
git pull --rebase下载并变基（历史更干净）

          
git log --oneline origin/main..HEAD我有哪些提交还没推

          
git log --oneline HEAD..origin/main远端有哪些提交我还没拉

          
git diff --check扫有没有漏掉的冲突标记

          
git revert <hash>安全地撤销一个已推送的提交

        

      

    


    

      
提交信息怎么写

      
不是强制，但团队看得懂、机器能解析的写法会省掉无数麻烦。社区通用的 Conventional Commits 约定长这样：

      

        
feat(localization)新增 Addressables 键值校验工具

        
fix(inspector)修复折叠分组展开后丢失展开状态的问题

        
refactorcore把 JSON 解析抽成独立工具类

        
docs补充 Unity 2019 LTS 兼容性说明

        
chore更新 .gitignore，忽略 Library 目录

      

      
中文完全没问题，团队能看懂比"符合规范"更重要。上面的结构只是让你以后想用 git log --grep 筛选时不会抓瞎。

这份教程故意不讲什么

      
教程也有边界。知道哪些东西你现在不用管，比什么都学一遍更有价值。

    


    

      

        
🌳git worktree

        
它解决的问题是"我想同时开两个工作区做不同的事"。听起来很美，但——

        
    
          
  • 每个工作区都是一份完整的项目副本
    • 
          
  • Unity 项目单份就动辄几个 G，Library/、Temp/ 全都要重建
    • 
          
  • 不像前端那样改完刷新浏览器就能看效果，要看效果必须真的打开 Unity，而同一份工程不能被两个 Unity 实例同时打开
    • 
        

        
很多开发了一年的人都没用过 worktree，这很正常。它在大型 C++ 项目和同时维护多个线上版本时才是刚需。
        对 Unity 项目的新手来说，它的成本远大于收益。等你开始同时维护 v1 和 v2 两个插件版本，再回来读它。

      


      

        
🪝底层对象模型（blob / tree / commit 对象）

        
知道"每个 commit 有个哈希、是个对象"就够用了。SHA-1 怎么算的、tree 怎么嵌套，Git 内部已经处理好了，初学阶段了解这些只会增加负担。

        
等到你需要写 Git 脚本或排查诡异的仓库损坏问题，再去读 Pro Git（全书免费）。

      


      

        
🧬submodule / sub-tree

        
在一个仓库里嵌套另一个仓库。除非你在做单体仓库（monorepo）或 SDK 分发，否则用不上。

        
Unity 项目如果需要引入第三方源码，更常见的是直接 git subtree add 或把代码作为包发布，而不是 submodule——submodule 对新手来说简直是噩梦。

      


      

        
🔀cherry-pick / revert 的高级用法

        
知道 git revert 能撤销一个已推送的提交、git cherry-pick 能从别的分支摘一个提交过来，就够日常用了。

        
更多花式操作（交互式 rebase、reflog 抢救、bisect 找 bug 引入点）都属于"出问题之后现学"的技能，不需要提前背。

1commit 是你的私人存档点，随时按

        
2push 之前的工作对团队不存在

        
3pull 会动你的代码，所以先 commit

        
4冲突时先保别人的逻辑，再把你的接上去

        
5拿不准就 git status，搞砸了还有 git reflog
