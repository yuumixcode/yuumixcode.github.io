场景管理没有最佳方案，只有和你规模匹配的那一个

单场景 + DontDestroyOnLoad、管理器场景、分层叠加、常驻缓存、分区流式、Addressables 内容层——把六个方案摊开，按「小游戏 / 微信小游戏 / 独立游戏 / 大型商业」四档给出推荐组合、真实代价与踩坑清单。

01

先把零件拆开：三个原语

所有"场景管理框架"都是这三个 API 语义的排列组合。先把语义钉死，后面讨论才不会飘。

REPLACE

替换 · Single

LoadScene(name, LoadSceneMode.Single)

官方语义：关闭所有当前已加载场景，再加载新场景。不是"只换主场景"。

副作用：自动调用 Resources.UnloadUnusedAssets，大面积卸载时会卡。

STACK

叠加 · Additive

LoadScene(name, LoadSceneMode.Additive)

在当前场景集上再加一层，互不销毁。UI、音频、内容可以各占一层。

副作用：生命周期、active scene、光照归属全靠自己管。

PERSIST

持久化 · 隐式 vs 显式

隐式：DontDestroyOnLoad(obj)，对象被挪进一个运行时伪场景——Play 时在 Hierarchy 里单独一栏，但不可打开、不可保存为资产。

显式：一个常驻的管理器场景，Hierarchy 里看得见、引用可序列化。

隐式（DDOL）长什么样

Boot ─┐
      │  DDOL 对象被挪到
      │  运行时伪场景
      ▼  （仅 Play 可见）
Game ──► 切换后仍在

显式（Manager Scene）长什么样

Boot ──► Manager(scene，常驻)
           ├─ Services
           ├─ UIRoot
           └─ Audio
Game(scene) 叠加或替换
Unity 手册原文：“It is recommended to avoid using DontDestroyOnLoad to persist manager GameObjects that you want to survive across scene loads. Instead, create a manager scene that has all your managers…” —— DDOL 是逃生舱，不是机房。
02

六个方案

A–E 是"场景结构"，F 是"资源层"，F 与 A–E 正交，可以叠加使用。

A

单场景流水线 + DDOL

最小可用

任意时刻只有一个内容场景，管理器与 UI 根挂在 DontDestroyOnLoad 上，靠 Single 一路替换：启动 → 主城 → 战斗。

  • 优势：心智负担最低，场景即状态机状态；单场景可独立 Play；光照/天空盒天然跟着场景走。
  • 代价：DDOL 重复实例、跨场景引用脆弱、UI 与生命周期脱钩、隐式常驻内存、无法表达"叠加态"。
适合：小游戏、原型、Jam。把 DDOL 限制在 UIRoot / Audio / Session 三类。
别用：需要无缝、需要关卡与常驻 UI 并存、需要远程下发场景。
Boot ──Single──► Main ──Single──► Battle
      └──── DDOL: Manager / UIRoot / Audio ────┘
         （每次切换，世界全量重建）
B

Bootstrap + 常驻管理器场景

官方推荐

Boot 只做初始化与首屏，然后把 Manager 场景叠进来；Manager 从头活到尾，承载服务、UIRoot、音频、配置。

  • 优势：层次显式可见；场景内引用可序列化；团队按场景切文件、冲突面小；契合 Addressables 分组。
  • 代价：多一个"几乎空"的场景要维护；加载顺序靠代码保证；Manager 里不能放渲染设置。
关键设计：内容场景根节点做"自举检查"，编辑器里从任意场景 Play 都能跑。
Boot(极薄) ─Additive─► Manager(常驻)
                         ├─Additive─► Menu
                         ├─Additive─► Main
                         └─Additive─► Battle
// 内容场景根节点：自举检查
static void EnsureManagerScene(){
  var s = SceneManager
      .GetSceneByName("Manager");
  if (s.isLoaded) return;
  SceneManager.LoadScene("Manager",
      LoadSceneMode.Additive);
}
C

分层叠加（全 Additive）

中大型主力

Manager 常驻，Gameplay / UI / Audio / VFX 各自成层。切关卡 = 加载新 Gameplay + 卸载旧 Gameplay，不再用 Single。

  • 优势：UI 与音频不随关卡重建，切场景无闪断；天然支持"加载中"场景；多状态可并存（战斗 + 暂停 + 过场）。
  • 代价：active scene 必须自己切（光照/天空盒/雾/导航都取自它）；卸载时序要设计；每个场景要有根节点约定。
为什么放弃 Single：Single 会把叠加的 UI、音频一起关掉，于是必然出现"闪一下"。
┌ UI Layer   (Additive) 常驻 ┐
├ Gameplay   (Additive) 换   │
├ Audio/VFX  (Additive) 按需 │
└ Manager    (Additive) 常驻 ┘
// 先加新的，再卸旧的，最后切 active
var load = SceneManager.LoadSceneAsync(
    next, LoadSceneMode.Additive);
while (!load.isDone) yield return null;

SceneManager.SetActiveScene(
    SceneManager.GetSceneByName(next));
yield return SceneManager
    .UnloadSceneAsync(_current);
D

常驻缓存 + 权重预算

无缝往返

场景全部 Additive 加载，离开时只停用根节点子物体；再进入变成"启用"而不是"加载"。为已加载场景维护总预算，超预算按 LRU/优先级淘汰。

  • 优势：二次进入几乎零加载；可按平台设预算（Switch vs PC）；邻居预加载让"走到门口"就已就绪。
  • 代价：初始化必须写 OnEnable；停用时要记住"本来关着的子物体"；预加载会卡帧——纹理上传造成 3–4 帧、每帧约 50 ms 尖刺；常驻内存峰值高。
适合：开放世界、区域高频往返、内存受限的卡带平台。
进场景：已加载 → 启用(OnEnable)
        未加载 → 加载
预算：Σ weight > budget
      → 按最久未用淘汰

E

分区流式加载

开放世界

世界骨架（地形索引、全局光照、导航、天空）常驻，区域场景按玩家位置加减。触发分两种：距离驱动（室外，用雾遮切换）与触发器驱动（室内，控制精确）。

  • 优势：世界尺度不受单场景限制；美术分块并行；编辑器多场景同开即可预览整关。
  • 代价：NavMesh 边界、光照/反射探针合并、遮挡剔除共享；流式过程与玩法抢预算；必须节流与设优先级。
DOTS SubScene 是这条路的一种实现形态：适合海量实体，但"实体流式"≠"场景流式"。
World(骨架，常驻)
 ├─ Zone_00_00 (Additive)
 ├─ Zone_00_01 (Additive)
 ├─ Zone_01_00 (Additive)
 └─ … 按距离/触发器加减
// 同帧只加载一个分区
Application.backgroundLoadingPriority
    = ThreadPriority.Low;
F

内容层：Addressables / AB / CDN

正交层

不改变场景结构，只改变"场景从哪来"：从 Build Settings 里的硬引用，变成可远端下发、可热更、按引用计数释放的内容。

  • 必须知道：Addressables.LoadSceneAsync 内部就是 SceneManager，参数语义一致；Single 会卸当前场景并触发 UnloadUnusedAssets；卸载必须用同一个 handle。
  • 代价：加载路径变长（catalog → 下载 → 加载）；隐式依赖导致同一资源被重复打包；句柄泄漏；编辑器 Play Mode 差异。
微信小游戏与商业项目的必备层：包体与热更都靠它。
Build Settings:  包体 ──► 场景（不可热更）
Addressables:    catalog ──► 本地/远端
                 ├─ 按需下载
                 ├─ 版本清单
                 └─ 引用计数卸载
// 卸载要用 handle
var h = Addressables.LoadSceneAsync(
    key, LoadSceneMode.Additive);
// …
Addressables.UnloadSceneAsync(h);

04

四档规模的落地建议

同样的 API，不同的预算与团队规模，落点完全不同。

选 A，最多 A + B 的简化版

Boot(加载+首屏) ──► Game ──► Result ──► Game
        DDOL: UIRoot / Audio / Session
场景数
就两个：Boot（初始化 + 加载条）和 Game（主玩法 + 结算）。别做分层叠加。
UI
DDOL 上一个 Canvas，面板用栈管理，切场景前统一 CloseAll()。
必做
把 SceneManager 调用封进一个约 30 行的 SceneFlow。以后要换 B/C，只改这一个文件。
别做
提前上 Addressables。它会把首包初始化从 0 变成几百毫秒，小体量项目不值得。
约束项限制对场景管理的影响
主包≤ 4 MB只放引擎运行时、Boot、加载 UI、少量字体图标
主包 + 分包≤ 30 MB资源必须走远程；本地只留索引与版本号
单个普通分包不限可按关卡/章节切分包
单个独立分包≤ 4 MB独立分包适合"活动关"这类冷启动内容

结论：B + F，禁止 D/E

首包
只放引擎 + Boot + 极简 UI。任何大图都不该在主包里；Resources/ 目录在这个平台约等于往主包塞资源。
场景
必须"薄"。一个场景塞三套美术资源，在低端机内存模型下就是闪退——宁可拆成两个可 Additive 叠加的场景。
进度
等待由两段组成：分包/AB 下载（网络）+ 场景加载激活（CPU）。两段都要反馈，否则玩家以为卡死。wx.loadSubpackage 返回的 LoadSubpackageTask 可拿 onProgressUpdate；wx.preDownloadSubpackage 做预下载。
常驻
DDOL 只放 UIRoot 与音频，音频源数量受控。iOS 低内存机型是闪退高发区。
切换
优先 Additive 换内容层，避免 Single 触发全量卸载 + 重建。

选 B + C + F

Boot ──► Manager(常驻: Services / UIRoot / Audio / Save)
            ├─ Menu        (Additive)
            ├─ Chapter_01  (Additive)
            └─ Battle      (Additive，与 Chapter 并存做转场)
切换
章节切换用 Additive；只有"回主菜单 / 重开一局"才用 Single——那时你确实需要一次彻底重置。
UI
独立成场景，常驻叠加在 Manager 之上，切关卡不闪断。
资源
Addressables 按「场景 + 共享依赖」分组：共享材质/图集单独一组，否则每个场景包各带一份。定期看 Build Layout Report。
效率
自举检查让团队能在任意场景按 Play，不用每次回 Boot。
还不需要
D 与 E。除非关卡间反复往返、加载时间已经明显影响体验。

B + C + D + E + F 全上，并且工程化

Entry
一个永不卸载的 EntryPoint/Persistent 场景，从启动活到退出，承载资源加载、场景加载、设置、相机、账号。
分层
Global Manager（永不卸）+ Sub-Global Manager（随状态装卸，如"战斗子管理器"）。避免一个 God Manager 活到天荒地老。
状态机
Boot → Login → Lobby → Matchmaking → Battle → Result，每个状态声明"要哪些场景 + 哪些服务"，由状态机做 diff。这才是商业级与能跑的区别。
三段式
准备（下载/依赖）→ 预热（Shader 变体、材质、对象池）→ 激活（allowSceneActivation）。只在最后一步切画面。
预算
场景带权重，总预算按平台配置；预加载服从预算；LRU + 优先级，而不是纯 LRU。
可观测
下载 / 反序列化 / 激活 / 首帧渲染分别埋点，否则线上"加载慢"永远只能猜。
05

UI 到底放哪：四种放法

这是最容易吵起来的架构决策之一，本质是"UI 该和谁同生共死"。

放法切场景表现状态保持协作主要风险适合
① DDOL Canvas不闪断手动管理UI 与场景分离面板残留、DDOL 重复实例小游戏、原型
② UI 独立场景不闪断场景内自然保留清晰，单独文件需管 active scene；Single 会连它一起关独立游戏、商业
③ 场景自带 Canvas随场景重建（会闪）随场景销毁与关卡强耦合每场景重复搭 UI；HUD 要复制强上下文界面、VR
④ 代码生成 / UI Toolkit完全可控由代码管理无场景文件冲突调试成本高、设计师不友好HUD、工具 UI
推荐组合：全局层（登录/设置/弹窗/Toast/加载条）→ ② 独立 UI 场景常驻；HUD 与战斗内界面 → ③ 跟随战斗场景一起卸载；编辑器调试面板 → ④ 代码生成、不进正式包。该常驻的常驻、该一起死的跟着死。
06

场景根节点（SceneRoot）规范

Unity 没有"场景级生命周期"：SceneManager 只告诉你加载完了，不告诉你这个场景该初始化什么、离开时该清什么。SceneRoot 就是补这个缺口的约定。

CONVENTION

每个场景只有一个顶层容器

场景里所有内容都是它的子节点，容器上挂 SceneRoot：无 Renderer、无 Collider、不做位移。

Battle.unity
└─ [Scene] Battle   ← SceneRoot
   ├─ Environment   ← 地形/背景/装饰
   ├─ Gameplay      ← 角色/敌人/交互物
   ├─ Lighting      ← 光照/反射探针
   ├─ Markers       ← 出生点/相机机位
   └─ Audio (可选)
WHY

它替身的是"场景"这个单位的回调

场景本身没有 Awake 和 OnDestroy。没有统一容器，你就无法"一句话停用一个场景"，也没有人对"离开时清理"负责。

方案 D（停用代替卸载）与方案 B（自举检查）都建立在这个约定上：前者要批量开关，后者要一个稳定的入口。

收益具体表现
生命周期收口初始化顺序收在 SceneRoot.Awake / Enter 里，而不是散在十几个 Start() 里靠执行顺序撞运气
整场景批量开关关掉 root 的子节点 = 这个场景休眠（方案 D 的前提）
干净的离开Exit() 集中停协程、退订事件、释放 Addressables handle、回收池；跨场景残留 bug 多因"没人负责清"
状态快照记住"进入时本来关着的子物体"，下次启用不误开（方案 D 最易忽略的坑）
查找与隔离从 root.Content 往下找，不用 GameObject.Find；层级稳定后可做场景 Prefab 模板
自举落点Awake 检查 Manager 是否加载、缺失就补——"从任意场景 Play"的实现位置
可工具化能写编辑器校验器：root 是否唯一、EventSystem 是否重复、光照是否烘焙
降低冲突层级形状固定，两人同改一个场景时冲突面小；美术与程序可按子节点分工
 
public sealed class SceneRoot : MonoBehaviour
{
    [SerializeField] SceneDefinition definition; // 元数据：显示名/加载组/权重/常驻
    [SerializeField] Transform content;          // 内容挂这里，root 自己不放东西
    readonly List<GameObject> _stayedDisabled = new();

    void Awake()
    {
        Bootstrap.EnsureManagerScene();   // 自举：任意场景 Play 都有全局上下文
    }

    public void Enter()
    {
        foreach (var go in _stayedDisabled)
            go.SetActive(false);        // 恢复"本来就关着"
        // 再触发本场景 View / Controller 初始化
    }

    public void Exit()
    {
        _stayedDisabled.Clear();
        foreach (Transform c in content)
            if (!c.gameObject.activeSelf) _stayedDisabled.Add(c.gameObject);
        // 停协程 / 退订事件 / 释放 handle / 回池
    }
}
四条反模式：① root 上写业务逻辑（会变 God Object，比没有 root 更糟）；② root 上挂 DontDestroyOnLoad（它代表"这一个场景"，不该活过它）；③ 一个场景多个 root（约定与工具同时失效）；④ 把 UI 和关卡塞进同一个 root（分层叠加要求 UI 能单独开关）。
概念职责生命周期放在哪
Bootstrap全局入口：设置、资源层、首屏进程级独立极薄场景，自己不做内容
SceneRoot场景容器与生命周期入口与场景同生共死每个场景唯一顶层物体
View / Controller局部表现与逻辑随所属对象root 的某个子节点下
顺手加个编辑器校验：扫描 Assets/Scenes/ 下所有场景，检查"顶层对象是否为 1 且挂 SceneRoot""content 是否为空""EventSystem / AudioListener / 主相机是否唯一"。约定只有能被机器检查才活得久。
07

十二个坑（按踩到概率排序）

前三条是"会改变架构决策"的坑，后面是可预防的工程细节。

1 · Single 会关掉叠加层

官方语义是"关闭所有当前已加载场景"。UI 场景、音频场景、Loading 场景都会没。要么全 Additive 自己卸，要么接受重建。

2 · allowSceneActivation=false 阻塞队列

progress 停在 0.9 只是表象；此时其它 AsyncOperation（如 UnloadSceneAsync）不会被调用，直到你设回 true。

3 · 忘了 SetActiveScene

光照、天空盒、雾、导航都取自 active scene。Additive 加载后不切，新关卡会沿用地形场景的光照。

4 · DDOL 重复实例

内容场景里再放一份管理器，场景重进一次就多一份。管理器只应来自 Manager 场景或 RuntimeInitializeOnLoadMethod。

5 · 进度条假死

直接用 async.progress 画条会卡在 0.9。要么映射 progress/0.9，要么自己按"下载 / 加载 / 激活"三段拼接。

6 · 多 Listener / EventSystem / Camera

每个场景各带一份，叠加后就报 "There are 2 audio listeners in the scene"。约定全局只有一个。

7 · 跨场景引用打包后断掉

编辑器里挂着的场景对象引用，进 Addressables 或换 Additive 后容易变 null。业务层只依赖接口与事件。

8 · 卸载顺序错

先卸逻辑（停协程、退订事件、清单例），再卸表现。反过来就会在已销毁对象上取组件。

9 · NavMesh / 探针 / 遮挡不合并

Additive 不会自动合并导航网格与探针。要么各场景各自烘焙并处理边界，要么统一在世界骨架里烘焙。

10 · 没有场景根节点约定

每个场景强制一个 SceneRoot，其下才是内容。Enable/Disable、批量清理、自举检查才有抓手（见 第 06 节）。

11 · 只能从 Boot 启动

团队被迫每次回 Boot 按 Play。加自举检查，从任意场景都能跑，效率差异非常直观。

12 · 小游戏包体与缓存

主包 4 MB 是硬红线；分包/AB 要考虑 CDN 缓存与版本号；首包体积每加 1 MB，转化率都在掉。

08

从「DDOL 单场景」迁移到「Manager + Additive」

不用重写。每一步都能独立提交、独立回滚，中途不会出现"改到一半跑不起来"。

  1. 抽一层门面新建 SceneFlow，把项目里所有 SceneManager.* 改成走它。不改行为，只收口。
  2. 建 Manager 场景把 DDOL 上的管理器、UIRoot、音频搬进去；Boot 改成 Additive 加载 Manager；删掉所有 DontDestroyOnLoad 调用。
  3. 加自举检查内容场景 SceneRoot.Awake 检查 Manager 是否加载，缺失就补。团队立刻能在任意场景 Play。
  4. 内容切换改 AdditiveSwitchContent 改成"加载新的 → SetActiveScene → 卸载旧的"。UI 与音频层从此不参与切换。
  5. 接资源层场景进 Addressables 分组，SceneFlow 内部换成 LoadSceneAsync 并保存 handle；对外 API 不变。
